Mission. Execute every single item in the plan, in order, without skipping, without reordering, without shortcutting. The plan contains hundreds of discrete tasks across mobile device matrix coverage, game flow state coverage, UI sizing audit, content completeness, API integration, performance and accessibility, KOSTAS state machine, save state edge cases, error handling, content production (NPC placements, dialogs, Pokemon, papers, TMs, items, signs), and automated test infrastructure. You do not get to pick which items are "important." Every checkbox in the plan  must end up checked with evidence attached. You are not allowed to mark a task complete until the evidence exists as a committed file on disk — a screenshot, a log, a test result, a diff, a commit hash. If you cannot produce evidence, the task is not done, regardless of how certain you feel. This is a ralph loop — the same prompt is fed back to you repeatedly, and each iteration must make measurable forward progress on the checklist. If an iteration makes zero forward progress, that is a failure state and you diagnose why before continuing.

Testing discipline — no change ships without proof. After EVERY code edit, no matter how small, you run Playwright against the dev server and take screenshots on at least three viewports: desktop 1440×900, mobile landscape 852×393, and mobile portrait 393×852. For each screenshot you use the Read tool to inspect the PNG pixels and write a one-line observation comparing expected vs actual. Then you dispatch touch or keyboard events that exercise the code path you just changed and verify via browser_evaluate that the underlying game state — Phaser scene, localStorage, React component state — matches expectations. You  also check browser_console_messages for any new errors or warnings. A change with a green build but no visual verification is NOT verified; the build only proves types compile, not that the UI is correct. Zero code changes are allowed to be committed without this four-step verification: screenshot on 3 viewports → read them visually → exercise the behavior → check console. If you skip this even once, you have broken the loop's discipline and you redo the last change.

Multi-persona user simulation. After verifying a change technically works, you simulate the experience from the perspective of five distinct user personas, one at a time: (1) a technical recruiter at Google who has 90 seconds to form an impression and zero patience for bugs; (2) a senior ML engineer who notices every off-by-one tile, every jittery frame, every misaligned pixel; (3) a mobile user on an iPhone SE holding a coffee one-handed who needs every touch target exactly where their thumb lands; (4) a colorblind visitor with prefers-reduced-motion on who can't distinguish the active d-pad arm from the inactive ones by hue alone; (5) a grandmother who has never played Pokemon and needs every UI affordance to be self-explanatory. For each persona you write a short internal monologue of what they see, what they try, what confuses them, what delights them, what makes them bounce. Any issue a persona raises becomes a new task to fix, which triggers the full testing discipline again. You are explicitly forbidden from dismissing a persona's complaint as "edge case" — if the complaint is real, it gets fixed.

Forced re-evaluation. After you fix something, you do NOT move on. You re-test the fix three separate times: once immediately, once after loading a clean fresh save, and once after reloading the page and walking back to the problematic state through the natural user flow. Each re-test takes a fresh screenshot, a  fresh console check, and a fresh state inspection. If any of the three re-tests shows a regression or a new edge case, the fix is incomplete and you start over. You are FORBIDDEN from using the word "should" in verification — "should" indicates hope, not evidence. Replace every "should work" with "verified working at [timestamp] on [viewport] via [method]." Additionally, once per Day's worth of tasks, you pick three already-green tasks at random and re-verify them from scratch to guard against invisible regressions. If a previously-green task is now red, everything from that task forward needs re-verification.

Anti-compromise clauses. The following are strictly forbidden and constitute a loop violation: (a) saying "this is good enough for now" without explicit authorization from the plan; (b) marking anything complete based on a type-check alone; (c) assuming without verifying; (d) skipping a viewport because "it probably works"; (e) trusting memory about a code path instead of re-reading the file; (f) using the word "should" in a completion claim; (g) emitting the completion promise while a single checklist item is unchecked; (h) telling yourself "I'll come back to it" — there is no coming back, there is only now; (i) fixing a symptom instead of the root cause — every bug has a root cause and you find it before declaring the fix done; (j) taking screenshots and not reading them visually; (k) batching three unrelated fixes into one commit to save time — each fix gets its own commit with its own evidence in the message. If you catch yourself doing any of these, you stop, acknowledge the violation in your work log, and redo the affected work properly from scratch.

Subagent validation for every moment of uncertainty. Every time you feel tempted to ask the user a question, instead spin up 5 independent general-purpose subagents with the same prompt and same context, each reasoning independently, and synthesize their answers into a decision. The subagents replace the user's judgment — if 4 of 5 agree on an approach, that's the approach; if split 3-2, spin up 5 more until you have 10 independent opinions, and go with the majority. Document the decision in a DECISIONS.md file so future iterations have a record of why. For any question that would normally require user taste (color choices,  copy tone, layout preferences), subagents fulfill that role — but you must actually dispatch them. Simulated subagents are a form of rationalization and count  as a loop violation. Every 50 tasks, you additionally pick the most-recently-closed task and ask a fresh subagent to independently verify it was actually done  correctly. If the subagent disagrees, the task reopens and you fix it again.

Completion criteria. The loop is not finished until every single one of the following is true, verifiable, and committed IN A SINGLE COHERENT VERIFICATION PASS — not at different points in time: (1) every task checkbox in the 10-day plan is checked with evidence attached; (2) every test in the Playwright suite passes on all three viewport categories; (3) zero console errors on /explore across the full user flow on desktop + mobile landscape + mobile portrait; (4) TypeScript compiles clean; (5) production build succeeds; (6) Vercel deployment is live and the deployed URL passes a full end-to-end test suite against real network conditions; (7) every NPC dialog is written, not stubbed, not placeholder; (8) every Pokemon, paper, TM, key item, blog post, sign, and Research Log entry has real content that reads like a human wrote it; (9) KOSTAS state machine handles all 7 priorities and has been tested with save fixtures for each priority branch; (10) all 5 API-powered NPCs actually fetch live data and fall back gracefully on failure; (11) the game has been screen-recorded from title screen through CHAMPION badge as a continuous playthrough without a single bug surfacing; (12) Lighthouse mobile score of at least 85 on /explore with touch mode forced. Until all twelve are simultaneously green in one pass, the loop continues.

You may only emit <promise>ALL_PHASES_COMPLETE</promise> after a final end-to-end run that begins by cloning the repo fresh into a temporary directory, running npm install, running npm run build, running the full Playwright suite to zero failures, deploying to a fresh Vercel preview URL, and playing  through the entire game from title to CHAMPION badge while a second independent subagent watches the run and writes an independent verdict that all twelve completion criteria are met. If the second subagent finds ANY issue, you fix it, and you restart the final verification run from the top — there is no partial credit on the final verification.
